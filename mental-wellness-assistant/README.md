# دستیار همراه ذهن — Mental Wellness Voice Assistant (Scaffold)

یک اسکلت (scaffold) کامل و قابل‌اجرا برای یک دستیار صوتی/متنی سلامت روان، با یک کدبیس React Native
(Expo) که هم‌زمان روی **iOS، Android و وب** اجرا می‌شود.

## ⚠️ اخلی مهم — محدودیت‌ها و مسئولیت (بخوانید)

- این پروژه **یک ابزار خودارزیابی غیرتشخیصی** است، نه یک محصول پزشکی. درصدهای «احتمال» با یک
  الگوریتم امتیازدهی ساده و ابتکاری (heuristic) تولید می‌شوند، نه یک مدل بالینی اعتبارسنجی‌شده.
- سؤالات از روی ساختار پرسش‌نامه‌های شناخته‌شده عمومی (شبیه PHQ-9، GAD-7، ASRS، MDQ، PC-PTSD-5،
  ISI، SCOFF، CAGE-AID) الهام گرفته شده‌اند اما بازنویسی و ساده‌سازی شده‌اند؛ **نسخه رسمی/دارای
  مجوز آن مقیاس‌ها نیستند** و نباید به‌جای آن‌ها بازاریابی شوند.
- بیماری‌هایی مثل **پارکینسون** یک اختلال عصبی-حرکتی هستند، نه روانی، و با پرسش‌وپاسخ صوتی قابل
  غربالگری نیستند. این اپ فقط چند علامت هشدار (لرزش، کندی حرکت، سفتی عضلات) را شناسایی و کاربر را
  به پزشک ارجاع می‌دهد — هرگز امتیاز روان‌پزشکی به آن نمی‌دهد.
- مسیر بحران (Crisis flow) طوری طراحی شده که **همیشه** ابتدا شماره‌های کمک اورژانسی و مشاوره را
  نشان دهد و تماس با فرد مورد اعتماد/اورژانس را تشویق کند؛ موسیقی و جوک فقط به‌عنوان کمک ثانویه
  *بعد از* نمایش منابع کمک واقعی ارائه می‌شوند، نه به‌جای آن‌ها.
- شماره‌های بحران در `src/data/crisisResources.ts` نقطه شروع منطقی هستند اما **باید پیش از هر
  استقرار واقعی، برای منطقه هدف بازبینی و به‌روزرسانی شوند**.
- بخش «مشاورهٔ زناشویی و روابط» راهکارهای عمومی و آموزشی می‌دهد، نه یک جلسهٔ مشاورهٔ واقعی؛ اگر
  پاسخ‌ها نشانهٔ خشونت یا کنترل شدید در رابطه باشد، به‌جای راهکار، کاربر مستقیماً به منابع کمک واقعی
  ارجاع داده می‌شود (`RelationshipSafetyScreen`)، همان‌طور که مسیر بحران خودکشی هم کار می‌کند.
- تمام داده‌های کاربر در این ریپو **ساختگی (synthetic)** هستند — هیچ داده واقعی بیمار وجود ندارد،
  و هیچ بک‌اند/پایگاه‌داده واقعی پیاده‌سازی نشده (طبق درخواست، داده‌های ورودی به‌صورت مصنوعی تولید و
  در کنسول چاپ می‌شوند: `npm run generate:synthetic`).
- قبل از هر استفادهٔ واقعی: با یک روان‌پزشک/روان‌شناس بالینی و یک متخصص حقوقی/رگولاتوری (به‌خصوص
  درباره مسیر ریسک خودکشی) مشورت کنید.
- «گوش فعال» یک **تشخیص صوتی/آکوستیک واقعی نیست** — فقط کلمات واضح گفته‌شده را که به متن تبدیل
  می‌شوند برای عبارات کلیدی بررسی می‌کند، هرگز خودش با اورژانس تماس نمی‌گیرد یا پیامک نمی‌فرستد (فقط
  برنامهٔ گوشی را با شماره/متن آماده باز می‌کند)، و فقط تا وقتی صفحه باز است کار می‌کند. جزئیات کامل
  در بخش «گوش فعال» پایین‌تر.

### جریان گفتگو (Screening flow)

1. کاربر «گفتگوی کامل» (تا ۱۰ سؤال) یا «سریع» (۵ سؤال) را انتخاب می‌کند.
2. ۶ تا ۸ سؤال هسته به ترتیب ثابت پرسیده می‌شوند: افسردگی، دو سؤال ایمنی/ریسک خودکشی (همیشه
   پرسیده می‌شوند)، اضطراب فراگیر، ADHD، بی‌خوابی، PTSD، و یک سؤال ارجاعی برای علائم حرکتی/عصبی.
3. اگر حالت «کامل» باشد، موتور بر اساس بالاترین امتیاز خوشه‌ها (افسردگی، اضطراب، ADHD، بی‌خوابی،
   PTSD) تا ۲ سؤال تکمیلی تطبیقی می‌پرسد (مثلاً افسردگی بالا → بررسی دوقطبی).
4. بعد از هر پاسخ، `crisisDetector` بررسی می‌کند؛ اگر ریسک تشخیص داده شود، گفتگو بلافاصله متوقف و
   کاربر به `CrisisScreen` هدایت می‌شود — صرف‌نظر از این‌که چند سؤال باقی مانده.
5. در پایان، `scoreSession` یک درصد «شاخص احتمال» ۰ تا ۱۰۰ برای هر بیماری قابل‌امتیازدهی محاسبه
   می‌کند و ۳ بیماری برتر برای پیشنهاد موسیقی/توصیه استفاده می‌شوند.

### موسیقی مورد علاقه (`FavoriteMusicScreen`)

کاتالوگ موسیقی روی سه محور برچسب‌گذاری شده تا بتوان با هر ترکیبی از آن‌ها جستجو/فیلتر کرد:
حال‌وهوا (mood)، باکلام/بی‌کلام (vocal)، و ایرانی/خارجی (origin) — `src/data/musicCatalog.ts`.
کاربر می‌تواند هنرمند/ژانر موردعلاقه و ترجیح باکلام‌وبی‌کلام/ایرانی‌وخارجی را ثبت کند (ذخیره‌شده
روی دستگاه با AsyncStorage، هرگز به جایی ارسال نمی‌شود)، و `musicSearchEngine.ts`:

- کاتالوگ محلی را بر اساس این علایق **رتبه‌بندی** می‌کند (`recommendForProfile`)،
- نتیجه را در ۴ دستهٔ باکلام‌ایرانی/باکلام‌خارجی/بی‌کلام‌ایرانی/بی‌کلام‌خارجی **دسته‌بندی** می‌کند
  (`categorizeTracks`)،
- و از طریق یک انتزاع `MusicSearchProvider` قابل **جستجو** است.

⚠️ **محدودیت مهم**: این اسکلت به اینترنت یا هیچ سرویس موسیقی واقعی (Spotify، YouTube Music، رادیو
جوان، Apple Music و …) متصل نیست و کلید API ندارد؛ تمام آهنگ‌ها **داده‌های ساختگی با نام‌های کاملاً
جعلی** هستند (برای پرهیز از نقض حق مالکیت معنوی/هویتی). دکمهٔ «جستجوی اینترنتی» در همین صفحه عمداً
به یک ارائه‌دهندهٔ نمایشی (`remoteInternetProvider`) وصل است که خطای صریح می‌دهد، نه این‌که وانمود کند
واقعاً در اینترنت جستجو کرده. برای اتصال واقعی، یک پیاده‌سازی واقعی پشت همین اینترفیس در
`src/engine/musicSearchEngine.ts` بنویسید — بقیهٔ اپ بدون تغییر کار می‌کند.

### راهنمای صوتی آشپزی (`RecipeScreen` + `CookingScreen`)

کاربر یک غذا را از بین ۱۲ آشپزی (ایرانی، فرانسوی، ایتالیایی، آمریکایی، چینی، فنلاندی، تایوانی،
مکزیکی، ژاپنی، هندی، تایلندی، مدیترانه‌ای — `src/data/cuisines.ts` و `recipeCatalog.ts`) انتخاب
می‌کند و دستیار او را **مرحله‌به‌مرحله و با صدا** راهنمایی می‌کند:

1. با شروع پخت، دستیار مرحلهٔ اول را با صدا می‌خواند (و در صورت نبود صدا، به‌صورت نوشتاری هم نشان
   می‌دهد — دقیقاً مثل بقیهٔ اپ، صدا هرگز اجباری نیست).
2. کاربر با صدا یا تایپ می‌گوید «بعدی» / «انجام دادم» تا مرحلهٔ بعد خوانده شود، «تکرار کن» تا همان
   مرحله دوباره گفته شود، «قبلی» تا برگردد، یا «تمام کن» تا آشپزی را متوقف کند —
   `engine/voiceCommands.ts#matchStepCommand` این عبارت‌ها را (فارسی و انگلیسی) تشخیص می‌دهد و
   `state/CookingContext.tsx` وضعیت مرحلهٔ فعلی را همان‌طور پیش می‌برد. همین تابع مشترک، پایهٔ
   دستورهای صوتی قصه‌گویی (پایین) هم هست.
3. با پایان آخرین مرحله، دستیار «نوش جان!» می‌گوید و کاربر می‌تواند به فهرست رسپی‌ها برگردد.

⚠️ **محدودیت مهم**: پایگاه‌دادهٔ رسپی یک **نمونهٔ اولیهٔ ۱۲ موردی و قابل‌گسترش** است، نه یک بانک
اطلاعاتی واقعی و نامحدود از «تمام غذاهای دنیا» — چنین چیزی نیازمند یک سرویس/دیتابیس رسپی واقعی
(مثل Spoonacular یا Edamam) است. طراحی `recipeEngine.ts` عمداً ساده نگه داشته شده تا افزودن رسپی
بیشتر، یا وصل‌کردن یک سرویس واقعی پشت همان تابع `searchRecipes`، بدون تغییر در صفحات اپ ممکن باشد.

### قصه برای کودکان (`StorytellingScreen` + `StoryPlaybackScreen`)

دستیار قبل از هر چیز، مثل یک گفتگوی واقعی، **سن و جنسیت کودک را می‌پرسد** (با صدا یا تایپ، از طریق
دکمه یا جواب آزاد)، سپس می‌پرسد قصه با «صدای مادرانه و مهربان» گفته شود یا «معمولی و ساده»:

1. بر اساس سن (۲ تا ۴، ۵ تا ۷، ۸ تا ۱۰، یا ۱۱ تا ۱۳ سال)، فهرست قصه‌های مناسب همان رده نشان داده
   می‌شود — `src/data/storyCatalog.ts` (۸ قصهٔ کاملاً اورجینال، نوشته‌شده برای همین اپ، نه اقتباس از
   قصه‌های موجود).
2. بر اساس جنسیت انتخابی، یک اسم قهرمان (پسرانه/دخترانه/خنثی) انتخاب و در تمام قصه جایگزین
   `{{NAME}}` می‌شود — `engine/storytellingEngine.ts#pickProtagonistName` + `renderParagraph`.
3. قصه‌گویی، بخش‌به‌بخش و با صدا انجام می‌شود؛ همان دستورهای صوتی آشپزی («ادامه بده»، «تکرار کن»،
   «قبلی»، «تمام کن») اینجا هم کار می‌کنند (`engine/voiceCommands.ts`، مشترک با `CookingContext`).
4. صدای قصه‌گو از طریق `voiceService.speakStory` پخش می‌شود که سعی می‌کند یک **صدای زنانه** روی
   دستگاه پیدا کند و بسته به سبک انتخابی، سرعت و زیروبمی صدا را تنظیم می‌کند: «مادرانه» کندتر و
   کمی زیرتر، «معمولی» با سرعت عادی گفتار.

⚠️ **محدودیت صادقانه دربارهٔ صدای زن**: نه `expo-speech` و نه Web Speech API هیچ فیلد «جنسیت صدا»ی
قابل‌اتکایی روی همهٔ پلتفرم‌ها ارائه نمی‌دهند. انتخاب صدای زنانه در `voiceService.ts` یک حدس مبتنی
بر نام‌های رایج صداهای iOS/Android/مرورگر است (مثل «Samantha»، «Zira»، «زهرا»)، نه یک تضمین قطعی —
روی بعضی دستگاه‌ها ممکن است فقط یک صدا برای هر زبان نصب باشد. برای کنترل دقیق و همیشگی روی صدا،
باید یک سرویس TTS ابری (مثل Google Cloud TTS یا Amazon Polly، که صدای زن فارسی/انگلیسی مشخصی دارند)
پشت همین تابع `speakStory` وصل شود.

### مشاورهٔ زناشویی و روابط (`CounselingScreen` + `CounselingResultsScreen`)

دستیار اول می‌پرسد کاربر در کدام دستهٔ زیر قرار می‌گیرد: **زن متأهل**، **مرد متأهل**، **دختر مجرد
در حال ازدواج**، یا **پسر مجرد در حال ازدواج**؛ این فقط برای متناسب‌کردن سؤال‌ها استفاده می‌شود
(مثلاً سؤال «آمادگی برای ازدواج» فقط برای افراد مجرد پرسیده می‌شود)، نه برای تغییردادن محتوای
راهکارها بر اساس جنسیت.

1. یک گفتگوی پرسش‌وپاسخ تطبیقی (شبیه به بخش غربالگری سلامت روان) دربارهٔ موضوعاتی مثل ارتباط
   کلامی، اعتماد، مسائل مالی، خانوادهٔ همسر، حل تعارض، انتظارات، تصمیم‌گیری مشترک و حسادت انجام
   می‌شود — `src/data/counselingQuestions.ts` + `engine/counselingEngine.ts`.
2. یک سؤال ایمنی **همیشه** پرسیده می‌شود (آیا همسر/نامزدتان با تهدید، کنترل شدید یا آسیب فیزیکی
   شما را ترسانده؟). اگر پاسخ یا متن آزاد نشانهٔ نگران‌کننده‌ای داشته باشد، گفتگو فوراً متوقف و کاربر
   به `RelationshipSafetyScreen` هدایت می‌شود — به‌جای فهرست راهکار، شمارهٔ خط کمک و توصیه به کمک
   حرفه‌ای/حقوقی نشان داده می‌شود. اگر متن آزاد نشانهٔ افکار خودکشی داشته باشد (نه لزوماً خشونت رابطه)،
   کاربر به همان `CrisisScreen` بخش سلامت روان هدایت می‌شود؛ این دو مسیر ایمنی کاملاً مستقل از هم عمل
   می‌کنند.
3. در پایان، بر اساس موضوع(های) با بیشترین نگرانی، چند راهکار از `relationshipStrategies.ts` انتخاب
   و **با صدا خوانده می‌شود** — دقیقاً همان چیزی که خواسته شد: «به‌صورت صوتی راهکار مناسب ارائه شود».

**دیتاست راهکارها**: ترکیبی از ۱۱ نکتهٔ اورجینال الهام‌گرفته از رویکردهای شناخته‌شدهٔ روان‌شناسی
(گاتمن، زوج‌درمانی هیجان‌محور سو جانسون، نظریهٔ دلبستگی جان بالبی، زوج‌درمانی ایماگو هارویل
هندریکس، ارتباط بدون خشونت مارشال روزنبرگ، گوش‌دادن فعال کارل راجرز، رفتاردرمانی شناختی آرون بک،
روان‌شناسی مثبت‌گرای مارتین سلیگمن، نظریهٔ سیستم‌های خانوادهٔ موری باوئن) و ۸ ضرب‌المثل اصیل فارسی
(مثل «زبان سرخ سر سبز می‌دهد بر باد»، «آشپز که دو تا شد...»، «صبر و ظفر هر دو دوستان قدیمند»)، هرکدام
با یادداشتی کوتاه دربارهٔ کاربرد امروزی‌اش. متن هر نکتهٔ روان‌شناسی **خلاصهٔ اورجینالی** است که برای
همین اپ نوشته شده (نه نقل‌قول از کتاب)، همراه با نام رویکرد/فرد به‌عنوان منبع الهام.

⚠️ **محدودیت‌های مهم**:

- این جریان **جایگزین یک جلسهٔ مشاورهٔ واقعی نیست** — `DISCLAIMERS.counselingNotSubstitute` در نتیجه
  همیشه نمایش داده می‌شود.
- دروازهٔ ایمنی (`assessRelationshipSafety`) یک ابزار غربالگری ساده با کلیدواژه و مقیاس است، نه یک
  ارزیابی خطر بالینی؛ برای شرایط واقعی خشونت خانگی، `RelationshipSafetyScreen` صراحتاً کاربر را به
  کمک حرفه‌ای/حقوقی ارجاع می‌دهد و هیچ توصیهٔ خاصی دربارهٔ «چه‌کار کند» نمی‌دهد (چون برنامه‌ریزی ایمنی
  نیازمند تخصص و شناخت کامل شرایط فرد است).
- شماره‌های `src/data/crisisResources.ts` (از جمله خط ملی خشونت خانگی آمریکا) باید پیش از هر استقرار
  واقعی، برای منطقهٔ هدف بازبینی و تکمیل شوند.

### تغذیه و تناسب اندام بر اساس BMI (`FitnessScreen` + `FitnessResultsScreen`)

دستیار می‌پرسد کاربر ورزشکار است یا نه، هدفش از ورزش سلامتی عمومی است یا ورزش حرفه‌ای/رقابتی، و از نظر
وزن به‌دنبال کاهش، افزایش یا حفظ وزن است؛ سپس قد و وزن را می‌پرسد (با صدا یا تایپ، اعداد فارسی هم
فهمیده می‌شوند) و شاخص تودهٔ بدنی (BMI) را حساب می‌کند. بر اساس دستهٔ BMI و پاسخ‌ها، چند راهکار تغذیه و
فعالیت بدنی از `src/data/fitnessStrategies.ts` انتخاب و **با صدا خوانده می‌شود**.

دو نکتهٔ ایمنی که `engine/fitnessEngine.ts` صریحاً بررسی می‌کند:

- اگر کاربر ورزشکار باشد، BMI به‌تنهایی می‌تواند گمراه‌کننده باشد (چون توده عضلانی را نادیده می‌گیرد)؛
  این هشدار همیشه کنار نتیجه نشان داده می‌شود.
- اگر هدف وزنی با وضعیت فعلی در تضاد نگران‌کننده باشد (مثلاً کسی با کمبود وزن به‌دنبال کاهش بیشتر وزن
  است)، یک هشدار غیرمسدودکننده نشان داده می‌شود که کاربر را به پزشک/متخصص تغذیه (و در صورت نیاز، به
  بخش غربالگری سلامت روان همین اپ) ارجاع می‌دهد — بدون این‌که از نمایش راهکارهای عمومی جلوگیری کند.

### گوش فعال (`ActiveListeningScreen`)

یک قابلیت کاملاً اختیاری (پیش‌فرض خاموش) که کاربر باید صراحتاً روشنش کند. وقتی روشن و این صفحه باز
است، دستیار گفتار اطراف را با همان سرویس تشخیص گفتار (`voiceService.listen`) به متن تبدیل می‌کند و
دنبال عبارات مرتبط با درگیری/نیاز پلیس، آتش‌سوزی، وضعیت پزشکی اورژانسی، یا فشار/اجبار
(`engine/activeListeningEngine.ts#detectEmergency`) می‌گردد:

- با تشخیص **درگیری/آتش/پزشکی**، صفحه فوراً پیام مناسب را با صدا اعلام می‌کند، موقعیت مکانی فعلی را
  (در صورت مجوز) به آدرس یا مختصات تبدیل و می‌خواند، و یک دکمهٔ «تماس با ۱۱۰/۱۲۵/۱۱۵» نشان می‌دهد —
  که فقط برنامهٔ تلفن گوشی را با شماره باز می‌کند؛ تماس واقعی را باید خود کاربر تأیید کند.
- با تشخیص **فشار/اجبار**، اگر پیش‌تر (با یک گفتگوی کوتاه پرسش‌وپاسخ) نام و شمارهٔ یک «دوست مورد
  اعتماد» ثبت شده باشد، دکمه‌ای برای باز‌کردن پیامک‌رسان گوشی با متن آمادهٔ «با من تماس بگیر، فوری!»
  به آن شماره نمایش می‌دهد (`expo-sms`؛ باز هم فقط بازکردن برنامهٔ پیامک، نه ارسال خودکار).
- برای اطمینان‌خاطر در شرایطی مثل حضور پرستار بچه در منزل، کاربر می‌تواند خلاصه‌ای از گفت‌وگوهای
  شنیده‌شده را هر ۳۰ یا ۶۰ دقیقه (یا فقط دستی، با دکمهٔ «دریافت خلاصه الان») دریافت و در صورت تمایل با
  پیامک برای مخاطب ذخیره‌شده بفرستد (`summarizeListeningPeriod`).

⚠️ **محدودیت‌های حیاتی که باید بدانید** (کامل در `DISCLAIMERS.activeListeningLimitations`):

- این یک **تشخیص صوتی/آکوستیک نیست**. صدای دعوا، شعلهٔ آتش، گریهٔ کودک یا لحن صدا را نمی‌شنود؛ فقط
  جمله‌هایی را که واضح گفته شوند و درست به متن تبدیل شوند، برای عبارات کلیدی بررسی می‌کند. برای
  سناریوی «پرستار بچه»، این یعنی خلاصهٔ دوره‌ای فقط می‌تواند بگوید *چند گفت‌وگو شنیده شد* و *آیا عبارت
  نگران‌کننده‌ای در آن‌ها بود*، نه این‌که رفتار پرستار خوب بوده یا او به گریهٔ کودک بی‌توجهی کرده —
  چنین قضاوتی نیازمند مدل واقعی تشخیص صدا/رفتار است که در این اسکلت پیاده‌سازی نشده.
- فقط وقتی این صفحه **باز و در پیش‌زمینه** است کار می‌کند؛ گوش‌دادن در پس‌زمینه یا وقتی گوشی قفل است
  در این اسکلت پیاده‌سازی نشده (نیازمند سرویس بومی پس‌زمینه و خروج از Expo managed workflow است).
- این اپ **هرگز خودش و بی‌اجازه** با اورژانس تماس نمی‌گیرد یا پیامک نمی‌فرستد؛ فقط برنامهٔ تماس/پیامک
  گوشی را با اطلاعات آماده باز می‌کند و لمس نهایی همیشه با کاربر است.
- اگر قصد دارید از این قابلیت برای نظارت بر یک پرستار/مراقب استفاده کنید، بسته به کشور و ایالت ممکن
  است ضبط یا پایش صدای فرد دیگری بدون اطلاع او از نظر قانونی نیاز به رضایت یا اطلاع‌رسانی داشته باشد؛
  پیش از استفادهٔ واقعی، این موضوع را بررسی کنید.
- شماره‌های `src/data/emergencyContacts.ts` (۱۱۰/۱۲۵/۱۱۵) مخصوص ایران هستند و باید برای منطقهٔ هدف
  تأیید/به‌روزرسانی شوند.

### رفیق همراه (`CompanionScreen`)

یک فضای گفتگوی روزانهٔ کوتاه که کاربر می‌تواند اسم خودش را بگوید، چند «فکت» دربارهٔ خودش ثبت کند
(«عاشق نقاشی‌ام»، …) و حال‌وهوای امروزش را از بین ۸ حالت (غمگین، مضطرب، عصبانی، بی‌حس، درمانده، تنها،
امیدوار، آرام) انتخاب کند. دستیار:

- با صدا/نوشتار یک جملهٔ همدلانهٔ ازپیش‌نوشته‌شده متناسب با همان حال‌وهوا می‌گوید
  (`engine/companionEngine.ts#reflectionForMood`، از `data/companionResponses.ts`)،
- در صورت وجود تاریخچهٔ حال‌وهوای چند روز اخیر، یک خلاصهٔ کوتاه («این چند روز اخیر بیشتر حس … رو ثبت
  کرده بودی») می‌گوید (`summarizeRecentMoods`؛ فقط شمارش، بدون هیچ تفسیر بالینی)،
- و بسته به حال‌وهوا، یک یا دو میان‌بر به بخش‌های مرتبط اپ (موسیقی، غربالگری، تغذیه، مشاوره، رسپی،
  قصه) پیشنهاد می‌دهد.
- هر چیزی که کاربر تایپ/بگوید در یک نوار گفتگوی سادهٔ «دفترچهٔ روزانه» ثبت و با یک جملهٔ کوتاهِ تأییدی
  («شنیدمت. حرف‌هات برام مهمه.») پاسخ داده می‌شود.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.companionNotRealAI`): این «رفیق همراه» یک مدل زبانی زنده
نیست و چیزی که کاربر می‌نویسد را واقعاً «نمی‌فهمد» — فقط اسم و فکت‌های صریحاً واردشده را روی دستگاه
ذخیره می‌کند و از بین جمله‌های از‌پیش‌نوشته‌شده، مناسب‌ترین را بر اساس حال‌وهوای انتخابی برمی‌گزیند.
هیچ درک واقعی از شخصیت، حافظهٔ گفتگویی بلندمدت، یا تحلیل احساسات از متن آزاد در این اسکلت پیاده‌سازی
نشده؛ برای یک همراه واقعاً «هوشمند»، این لایه باید به یک مدل زبانی واقعی (با رعایت کامل حریم خصوصی و
رضایت کاربر) وصل شود.

### ترک عادت (`QuitCoachScreen`)

یک صفحهٔ دوبخشی برای ترک تدریجی سیگار، الکل، مواد مخدر یا هر عادت رفتاری دیگر:

1. **راه‌اندازی**: کاربر نوع اعتیاد، میزان مصرف روزانه (اختیاری)، سال‌های عادت (اختیاری)، تعداد
   تلاش‌های قبلی (اختیاری)، محرک اصلی (استرس/جمع دوستانه/بی‌حوصلگی/روتین/میل جسمی/غیره)، و دلیل شخصی
   ترک (اختیاری) را با صدا یا تایپ وارد می‌کند. `engine/quitCoachEngine.ts#buildQuitPlan` از
   `data/quitCoachStrategies.ts` یک برنامهٔ تدریجی ۵-۶ مرحله‌ای (متناسب با نوع اعتیاد) به‌علاوهٔ یک
   قدم اضافه برای محرک انتخاب‌شده می‌سازد؛ اولین قدم با صدا هم خوانده می‌شود.
2. **چک‌این روزانه**: کاربر هر روز (حداکثر یک ثبت در روز) می‌گوید امروز مصرف داشته یا نه، سطح میل
   (۰ تا ۵)، و یک یادداشت اختیاری — همه روی دستگاه با AsyncStorage ذخیره می‌شود
   (`state/useQuitCoach.ts`). `computeStreak` تعداد روزهای متوالی بدون مصرف و میانگین میل را محاسبه
   می‌کند، و `encouragementForCheckIn` بسته به نتیجهٔ امروز یک پیام تشویقی یا دلگرم‌کننده (بدون
   قضاوت، برای روزهای لغزش هم) می‌گوید.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.quitCoachMedicalSupervision`، همیشه برای الکل/مواد مخدر
نشان داده می‌شود): این «دستیار روزانه» جایگزین سم‌زدایی پزشکی نیست. ترک ناگهانی یا بدون نظارت الکل یا
برخی مواد می‌تواند از نظر پزشکی خطرناک باشد (حتی تشنج یا عوارض جدی)؛ برنامهٔ این بخش برای این دو نوع
عمداً کلی و محتاطانه نوشته شده و همیشه با توصیهٔ صریح مراجعه به پزشک یا مرکز ترک اعتیاد همراه است. این
اپ هیچ «بازخورد روزانهٔ» واقعی مثل نوتیفیکیشن یادآوری یا پیگیری خودکار ندارد — چک‌این کاملاً به ابتکار
خود کاربر و در همین صفحه انجام می‌شود.

### مشاور شغلی و کارآفرینی (`CareerCoachScreen`)

یک مسیر دوبخشی برای کسی که به‌دنبال شغل یا درآمد است:

1. **تشخیص روحیه**: با ۳ سؤال ساده و تراشه‌ای (نه تحلیل متن آزاد) — امنیت شغلی در برابر پتانسیل رشد،
   دنبال‌کردن دستورالعمل در برابر تصمیم‌گیری مستقل، و میزان تحمل ریسک — `engine/careerCoachEngine.ts#inferMindset`
   تشخیص می‌دهد روحیه بیشتر «کارمندی» است یا «کارآفرینی» (اکثریت ۲ از ۳ پاسخ).
2. **انتخاب مسیر**: بر اساس روحیه، ۳ مسیر پیشنهاد می‌شود — کارمندی: رزومه‌نویسی و ارسال درخواست،
   کارآموزی، مهارت‌افزایی؛ کارآفرینی: فریلنسری، راه‌اندازی کسب‌وکار، مهارت‌افزایی
   (`data/careerStrategies.ts#PATHS_BY_MINDSET`).
3. **چک‌لیست و دفترچهٔ پیشرفت**: هر مسیر یک چک‌لیست ۵ مرحله‌ای دارد (مثلاً برای فریلنسری: انتخاب
   خدمت، ساخت پروفایل، تعیین قیمت، تماس با مشتری، تحویل اولین پروژه) که کاربر خودش علامت می‌زند، به‌علاوهٔ
   یک دفترچهٔ آزاد برای ثبت روزانهٔ «امروز چه قدمی برداشتی؟» — همه روی دستگاه با AsyncStorage ذخیره
   می‌شود (`state/useCareerCoach.ts`).

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.careerCoachLimitations`): این بخش نه کارشناس استخدام واقعی
است، نه رزومهٔ کسی را می‌نویسد، نه به هیچ سایت کاریابی وصل است (این اپ اصلاً بک‌اند/اینترنت ندارد).
تشخیص روحیه فقط از ۳ پاسخ ساده است، نه یک ارزیابی روان‌شناختی واقعی. «دنبال‌کردن کاربر تا موفقیت
نهایی» با این چک‌لیست و دفترچه، به‌صورت کاملاً محلی و به ابتکار خود کاربر شبیه‌سازی شده — نه یک سیستم
واقعی یادآوری یا پیگیری خودکار.

### پیدا کردن آهنگ (`SongIdScreen`)

کاربر می‌تواند نام آهنگ، نام خواننده، یا چند کلمه‌ای که به‌خاطر دارد را با صدا یا تایپ وارد کند.
`engine/songIdEngine.ts#identifyByText` این متن را با تطبیق تقریبی (بر اساس فاصلهٔ ویرایشی
Levenshtein و بررسی زیررشته) با عنوان/خوانندهٔ کاتالوگ محلی موسیقی مقایسه می‌کند و بهترین نتیجه‌ها را
به‌همراه درصد شباهت برمی‌گرداند. برای چند آهنگ از کاتالوگ (`data/songLyricsPlaceholders.ts`)، یک
«لیریکس» نمایشی کاملاً ساختگی هم قابل‌نمایش است تا مسیر «نمایش لیریکس» در کد قابل تست باشد.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.songIdLimitations`): این بخش هیچ فناوری واقعی تشخیص صدا یا
اثرانگشت صوتی (audio fingerprinting) ندارد — نمی‌تواند به زمزمهٔ کاربر یا کلیپ صوتی پخش‌شده گوش بدهد و
آهنگ را تشخیص بدهد؛ فقط تطبیق متنی روی اسمی است که خود کاربر می‌گوید یا تایپ می‌کند. تطبیق فقط با
کاتالوگ ساختگی همین اپ انجام می‌شود، نه اینترنت یا هیچ آرشیو واقعی، و تمام آهنگ‌ها/لیریکس‌ها کاملاً
اورجینال و غیرواقعی‌اند. برای تشخیص واقعی از روی صدا یا لیریکس واقعی،
`engine/songIdEngine.ts#audioRecognitionStub` و `#remoteLyricsProviderStub` نقطهٔ اتصال مستندشده‌ای
برای سرویس‌های دارای مجوز (ACRCloud/AudD برای تشخیص صدا، Musixmatch/Genius برای لیریکس) هستند —
هر دو عمداً پیاده‌سازی نشده‌اند و به‌جای وانمودکردن، خطای صریح می‌دهند.

## اجرا

```bash
npm install
npm run web       # اجرای نسخهٔ وب
npm run ios       # نیازمند Xcode/شبیه‌ساز iOS یا Expo Go
npm run android    # نیازمند Android Studio/شبیه‌ساز یا Expo Go
npm run start      # منوی Expo Dev Tools (انتخاب پلتفرم از آنجا)

npm run test        # تست‌های Jest برای موتور غربالگری/تشخیص بحران
npm run typecheck   # بررسی نوع با TypeScript
npm run generate:synthetic   # تولید کاربران ساختگی و چاپ نتیجهٔ موتور در کنسول
```

## نکات فنی مهم

- **صدا**: `expo-speech` برای تبدیل متن‌به‌گفتار روی هر سه پلتفرم کار می‌کند. تشخیص گفتار
  (speech-to-text) فقط در مرورگرهایی با پشتیبانی از Web Speech API (مثل Chrome) فعال است؛ روی
  iOS/Android به‌صورت خودکار غیرفعال است و کاربر باید تایپ کند — برای افزودن STT بومی واقعی،
  پکیجی مثل `expo-speech-recognition` یا یک API ابری را پشت همین `VoiceService` وصل کنید.
- **موسیقی**: کاتالوگ در `musicCatalog.ts` عمداً فقط داده (متادیتا) است، به‌جز یک تُن صوتی تولیدشده
  که برای اثبات صحت مسیر پخش (`expo-av`) گنجانده شده. در تولید واقعی این بخش باید به یک سرویس
  موسیقی دارای مجوز وصل شود.
- **حریم خصوصی**: هیچ داده‌ای در دستگاه ذخیره یا به سروری ارسال نمی‌شود؛ همه‌چیز در حافظهٔ نشست
  (session) می‌ماند و با شروع گفتگوی جدید پاک می‌شود. برای استفادهٔ واقعی، ذخیره‌سازی، رضایت کاربر
  (consent) و انطباق با قوانین حریم خصوصی داده‌های سلامت (مثل HIPAA/GDPR) باید طراحی شود — این
  اسکلت عمداً آن‌ها را پیاده‌سازی نکرده است.

## گام‌های بعدی برای تبدیل به محصول واقعی

1. بازبینی بالینی کامل بانک سؤال و آستانه‌های امتیازدهی توسط متخصص سلامت روان.
2. جایگزینی امتیازدهی ابتکاری با مدل/مقیاس‌های دارای مجوز و اعتبارسنجی‌شده.
3. اتصال STT بومی واقعی (iOS/Android) و یک سرویس موسیقی دارای مجوز.
4. طراحی مسیر تشدید انسانی (human escalation) واقعی برای موارد بحرانی، نه فقط UI.
5. پیاده‌سازی ذخیره‌سازی امن، رضایت‌نامه، و انطباق قانونی/رگولاتوری منطقه هدف.
